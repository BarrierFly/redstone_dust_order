# 红石粉更新顺序 · Redstone Dust Update Order

按 **原版更新红石粉及其六个邻居的先后顺序** 给每一块红石粉染色，让平时看不见的
`HashSet` 迭代顺序变成世界里能看出来的纹理。

纯客户端。不需要服务端安装，没有协议，没有数据包。

---

## 你看到的是什么

原版会把某个红石粉位置的七个"更新核"——它自己加六个邻居——塞进一个
`java.util.HashSet<BlockPos>`，插入顺序固定为
`自身、-Y、+Y、-Z、+Z、-X、+X`。`HashSet` 遍历时按桶号升序，同桶内按插入顺序。
得到的顺序在整个世界里并不一致，而且肉眼完全看不出来。

这个 mod 给每一种顺序分配一种颜色，于是一片平坦的红石粉会变成可读的三维图案。
铺一条长红石粉线，就能看出顺序在哪里翻转。

**怎么开启：** 默认关闭。到 *选项 → 控制 → 杂项* 里给
`redstone_dust_order.key.toggle` 绑一个键，然后按它；或者用 `/rsusoc on`。

## 三套调色板

内置三套，可随时切换。默认的是**为了看清而设计**的那套。

| | |
|---|---|
| **高对比**（默认） | 占约 97% 区块的 6 种顺序用 6 种对比强烈的颜色，其余用一族低饱和灰蓝。 |
| `3 组分组` | 浏览器模拟器的模式：3 个色相 × 2 个明暗共 6 色给六种主图案，其余统一灰色。 |
| `更新顺序` | 模拟器的傅里叶嵌入，60 种顺序各有各的颜色。忠于原版，但**只适合探索**：这 60 种颜色里有两色在 RGB 上只差 8 左右，细红石粉线根本分辨不出来。 |

默认为什么不用那套好看的：设计笔记实测傅里叶调色板里有一对顺序的颜色只差 9/255，
而其中一种占了全部区块的 24.3%。高对比那套是手工挑的，然后**按量化指标验证**过：
把原版贴图灰阶（254/235/217，对应增益 0.996/0.920/0.851）都算进去，最差的一对
仍然相距 112.8。改坏会有一条测试直接失败。

## 混色 alpha

`alpha = 1`（默认）完全替换原版颜色。小于 1 时按
`mix(原版电平色, 顺序色, alpha)` 混合，这样能保留一点信号强度，同时仍然能读出图案。
`0` 就是纯原版。

## `/rsusoc`

```
/rsusoc                      当前设置、顺序总数、配置文件路径
/rsusoc on | off             开关
/rsusoc palette <名字>       high_contrast | group3 | fourier
/rsusoc alpha <0.0 - 1.0>    混色系数
/rsusoc check                针对你当前所在位置重新推导一遍模型
```

`check` 是有意思的那个。它完全不用查找表、直接从算式重算七个桶号和遍历顺序，确认
查找表与之一致，并把你这个位置的完整推导打印出来，方便你跟浏览器模拟器在相同坐标上
对照。

**`check` 做不到的事：** 它无法验证原版真的走了 `HashSet` 这条路。那需要 mixin 加抓包，
而这个 mod 有意两者都不做。它能验证的是：查找表与生成它的模型仍然一致。

## 渲染方式

只替换 `minecraft:redstone_wire` 的方块 tint，仅此而已。

红石粉的贴图是纯中性灰（形状完全来自 tint），所以换掉 tint 就是全部工作。没有模型、
没有贴图、没有图集、没有渲染层、没有 shader。正因如此它和**任意**资源包、光影包都能
共存——它根本不碰它们要替换的那些文件。F3+T 表现也正确。

注册走的是原版自己的 `BlockColors#register`，而不是 Fabric 的
`ColorProviderRegistry.BLOCK`。Fabric 那个 API 在原版已经有 tint 提供者时是"包装"而不是
"替换"，而这里正是这种情况，所以它其实替换不掉。原版的注册最终落到一次普通的
`List#set`，所以在 `createDefault()` 之后注册就是直接覆盖。

**后果：** 原版把信号强度也编码在同一个 tint 里，接管 tint 就等于丢掉电平显示，除非用
`alpha` 或者资源包。用透明的 `redstone_dust_overlay` 图层恢复电平显示的配套资源包是
独立交付物，不在本仓库内。

tint 会烘进区块顶点色，所以 mod 只标脏，并在下一个 tick 统一重建一次。它绝不在渲染帧
内部重建——那会导致每一帧都重新网格化所有区块。

## 模型的全部内容

```
hashCode = x + 31y + 961z          // Vec3i.hashCode；BlockPos 没有覆写它
hash     = hashCode ^ (hashCode >>> 16)
bucket   = 15 & hash
```

`hashCode` 里只有三个数有用：

- `L` = 低 16 位
- `A` = 低 4 位
- `B` = 第 16..19 位

某个核的邻居 hash 是 `h + delta`，`delta` 是定值，所以它的桶号是
`((A + delta) & 15) ^ ((B + carry) & 15)`，其中 `carry` 是 −1/0/+1，取决于邻居的低半字
有没有跑出 0..65535。而哪些核会跑出去，只取决于 `L`：

| `L` | 模式 | 受影响的核 |
|---|---|---|
| 0 | 6 | 借位 `{-Z,-Y,-X}` |
| 1 – 30 | 5 | 借位 `{-Z,-Y}` |
| 31 – 960 | 4 | 借位 `{-Z}` |
| 961 – 64574 | 0 | 安全 |
| 64575 – 65504 | 1 | 进位 `{+Z}` |
| 65505 – 65534 | 2 | 进位 `{+Z,+Y}` |
| 65535 | 3 | 进位 `{+Z,+Y,+X}` |

于是 `(模式, A, B)` —— 7 × 16 × 16 = **1792** 种组合 —— 就完全决定了七个桶号，
进而决定整个遍历顺序。这就是全部查找表：启动时构建一次，之后只读。每个方块四次整数
运算加两次数组读取，没有分支、没有浮点、没有分配。

表里存的是**顺序编号**而不是颜色。这样切换调色板或 alpha 就是免费的，除了区块网格
不需要重建任何东西。

### 这套模型算出来是什么

穷举全部 2²⁰ 个 `(B, L)` 组合，恰好出现 **60** 种不同顺序：

| 编号 | 遍历顺序 | 占比 |
|---|---|---|
| 0 | `-Y → +Z → +X → O → +Y → -Z → -X` | 24.26682% |
| 1 | `+Y → -Z → -X → O → -Y → +Z → +X` | 24.26682% |
| 2 | `-Y → +Z → +X → +Y → -Z → -X → O` | 12.13341% |
| 3 | `+Y → -Z → -X → -Y → +Z → +X → O` | 12.13341% |
| 4 | `O → -Y → +Z → +X → +Y → -Z → -X` | 12.13341% |
| 5 | `O → +Y → -Z → -X → -Y → +Z → +X` | 12.13341% |
| 6 – 59 | … | 合计 2.93% |

6 种主顺序，约 97%。其余集中在一片沿 X 拉长的窄条里 —— 那是 hash 跨过 16 位边界的地方，
X 方向约 1922 格、Y 约 62 格、Z 只有 2 格，所以实际看到的是偶尔出现的长条纹。

这 6 种主顺序恰好就是结构干净的那几种：粉块本身，加上各自同桶的两组三个
（`{-Y,+Z,+X}` 和 `{+Y,-Z,-X}`）。只要这个结构成立，遍历就一定是"三个连续的组"，
变的只是哪个组排第一 —— 这就是 `3 组分组` 调色板，它的 6 种颜色。也正因为如此，
那个 97% 正好等于安全模式所占的比例。

### 对设计笔记的两处修正

两处都是"去验"而不是"去读"才发现的，并且都有测试钉住：

1. **图案并非严格 16 格周期。** `A` 是严格周期的 —— 沿任一轴平移 16 格，hash 增加
   16、496 或 15376，都是 16 的倍数。但桶号还取决于 `B`，而沿 Y 或 Z 平移 16 格加的是
   496 或 15376 而不是 16，所以在 `L` 较大时会越过某个邻居开始进位的点，顺序就变了。
   离边界远的时候成立，靠近边界就失效。

2. **单个 16³ 的格子只能看到 6 种主顺序里的 3 种。** 一个格子内部 `B` 是固定的，而顺序
   又依赖 `B`。要跨格子采样才能看全 6 种。

## 诚实的局限

- 整个模型建立在"原版用 16 桶的 `HashSet`、以 `Vec3i.hashCode()` 为键"之上。如果将来
  原版改了，**这个 mod 会静默失效** —— 它会继续自信地给出错误的颜色。请用
  `/rsusoc check`，并与模拟器对照。
- `redstone_experiments` 实验特性包（26.x）会直接把更新顺序随机化。mod 会检测到并在聊天
  里警告一次，`/rsusoc check` 也会报告，但**不会自动关闭自己** —— 悄悄改变玩家看到的
  东西，比告诉玩家"这里没有意义"更糟。
- 26.x 还有一个固定的 `NeighborUpdater.UPDATE_ORDER` 常量，看起来和 `HashSet` 模型矛盾。
  这一点还没有追到结论，见 `AGENTS.md` 的 *未决问题*。
- 26.x 下的光影表现没有在真实硬件上验证过。
